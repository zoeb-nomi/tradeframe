  2. every 15 minFill Ingest writes the ledger n8n reads the new IndMoney mail, parses each order into a trade_ledger row and adjusts cash inside positions_state. Stop fills get a 🚨 Telegram alert straight away.
  3. 19:00–01:30 IST · every 30 minMarket Watch does the stop math Through the US session it pulls prices in batches of six, reads positions_state, and works out stop proximity, exact raise-stop instructions and take-profit touches — then sends the Telegram alert and its spoken version.
  4. 16:45 ISTThe Nightly Screen The screen pulls 260 daily bars for all 45 universe symbols and rewrites screen_results. No Telegram message: this exists purely to give the brain a terminal to read.
  5. 17:00 ISTMCP hands over live state The State Export bridge serialises positions_state, trade_ledger and the fresh screen into one payload. Without it the brain would be reasoning from a memory of yesterday.
  6. 17:00 ISTThe brain researches the world Claude reads that state, then goes out for news, earnings, sector and macro, checks re-entry candidates and cash deployment, and decides what — if anything — should change. Since v2.7 it runs the FRM pre-compute first and judges from those numbers, then writes its FRM SHADOW block — regime, cash target and reason, proposals, declines — every session, qualifying candidates or not.
  7. 17:00 ISTBrief Intake writes it down Everything the brain decided comes back through the Brief Intake bridge as structured rows: daily_brief and pending_action for tonight, plus a copy in recommendations so the call can be graded later. A second, separately gated call carries the FRM's own proposals into the same scoreboard under author frm-shadow.
  8. 18:00 ISTThe digest goes out n8n reads the brief and the pending actions and sends one Telegram message — actions first, each with a ✅ button — followed by an mp3 of the same thing. An hour before the US open.
  9. 18:00–19:00 ISTYou are the executor You place the order in IndMoney yourself, then tap ✅. That tap is what writes the new stop back into positions_state — the system never assumes you acted.
  10. on the next fillAnd the loop closes Your order fills, IndMoney emails the confirmation, and Fill Ingest picks it up within fifteen minutes. Nothing in this diagram has an end — that is the whole design.
  11. 02:15 ISTThe scorer keeps it honest A side branch off memory: every recommendation that has come due at 5, 20 or 60 days is graded against what actually happened, and the grade goes back into the same table.

07When something looks wrong

Symptom on the left, what it actually means on the right.

No alerts all session
That is now distinguishable from a dead system — the 1:35 AM heartbeat fires either way. If the heartbeat arrived, silence was correct.
A workflow broke
Check the Monitoring — Trading OS chat first. Every workflow is wired to the global failure handler, so a break announces itself. Then the n8n executions tab.
Tables drifted from reality
Send a portfolio screenshot. Vision diff → Apply. That is always the fastest path back to truth.
Digest says "actions: none" but the brief describes an action
The reconciliation pass works — Build Digest cross-reads the brief text against the resting stops and surfaces the mismatch. But it was finding the level by matching the brain's prose, and on 18 Aug a differently-phrased action walked straight past it, so the claim that this was "structurally impossible" was too strong. The level now comes from pending_stop_level, not from wording. See the original post-mortem and the one that falsified it.
Audio arrived flat or mispronounced
The spoken script is composed separately from the text, in Build Spoken Text / Build Reply Voice / Build Alert Voice. Ticker names and shorthand expansions live there.
A number in a message looks stale
last_price comes from the last Market Watch poll — 30-minute cadence, and frozen outside US market hours.
The brief has no FRM block
The pre-compute did not answer. The run is flagged FRM_PRECOMPUTE_UNAVAILABLE and the brain carries on without it: the primary brief is unaffected, and arming is skipped entirely rather than run on stale numbers. Check MCP — FRM Precompute in the n8n executions tab.
The FRM says the calendar is clear
Check that it isn't empty. An empty macro_calendar silently yields event_clear=true in FRM Compute — indistinguishable from a genuinely quiet week, and it hands the regime score that point either way. A macro_empty flag is the fix and is not built yet.

Details 9 notes
  • Config-driven hysteresis. The band deciding whether a stop move is "real" enough to alert on is market_watch.ratchet_hysteresis_pct = 0.25%, not a hardcoded 1%. The old 1% band was silently suppressing genuine raises — the NVDA 179.70 → 180.79 case is what motivated the change.
  • Advisory alerts on overrides. Positions with manual_override set (TSM, OUST) still generate an advisory alert when the ratchet math would have raised the stop. Visible, not silent, even though the auto-raise is deliberately skipped.
  • Guarded stop levels on the alert buttons. Collect Alerts mints the ✅ Done / ⏰ Later pair on a breach, and since v2.6 the level those buttons carry comes from the shared psLevel reader — pending_stop_level first, an anchored regex only as a transitional fallback, then guards for finite, above the resting hard_stop, below last_price and not below half of it. The node now emits hard_stop with the alert so that guard is live rather than inert. No valid level, no button.
  • Successful runs are recorded again. saveDataSuccessExecution had been set to none on 16 Aug to suppress a daily no-op. The runs never stopped — only the record of them did, and an empty execution list later read as a two-session outage that had not happened. Restored to all.
  • The market-hours gate is DST-aware. It used to be a hardcoded EDT window, correct through summer and an hour wrong from 1 Nov. Since 21 Aug (private) the session is resolved in America/New_York, so the switch to EST costs nothing. Verified over a 37-case boundary matrix and a 7,200-minute old-vs-new regression, zero mismatches.
  • It watches armed conditions too. Since v2.7 a second chain runs beside the stop monitoring: it reads the conditions the brain armed last night, re-validates the Tier 1 rails against the live book at fire time rather than the book at arming time, and latches each row once so a condition cannot fire twice. The quote batch was widened from held names to held ∪ armed to feed it. The Telegram fire message exists but is reachable only through an explicit frm_enabled branch, so while the switch is 0 a true condition is recorded and nothing is sent. This took the workflow from 31 to 48 nodes — see the FRM card.
  • End-of-session heartbeat at 1:35 AM, gated by market_watch.heartbeat_enabled.
  • Audio on every alert as of v2.5. All six alert-send branches fan into one shared speech chain.
  • Credit cost ~65 of the 800/day free TwelveData allowance.

The FRM shadow route added v2.7

The brain now calls Brief Intake twice. The first call is the brief as it always was. The second carries only the FRM's proposals, logged to recommendations under author frm-shadow, and is made only once the first has returned ok:true.

  • Structurally gated, not politely gated. The shadow branch is its own path and cannot reach daily_brief or positions_state at all. The safety latch: a shadow call omits brief_text, so the pre-v2.7 intake would have rejected it with zero writes.
  • The price is server-derived. price_at_rec comes from screen_results, not from the payload — a caller cannot post the price its own call will later be scored against. Inserts are deduped.

How audio is produced

Three separate places now speak — the digest, Claude's replies, and market alerts — but all three use the same shape, so there is exactly one pattern to understand and one place per surface to tune.

Why an HTTP node and not the n8n OpenAI node

The built-in node cannot pass instructions — the parameter that makes gpt-4o-mini-tts steerable. Its schema exposes only model, input, voice, response_format and speed. Without instructions the read is flat regardless of voice. Audio moved off that node permanently on 14 Aug.

06The rules the system enforces for you

Since v2.7 these are not all the same kind of rule. Tier 1 rails are validated in code and never crossed. Tier 2 bands are defaults the FRM steers toward and may breach only in writing. Tier 3 is its judgment in between — and that is the part being scored.

  • Stops ratchet up only. Trail % below the 20-day high — Core 20%, Amplifier 15%. Manual overrides (TSM, OUST) are never auto-raised, but they do now generate advisory alerts.
  • Never hold a tight stop through earnings. Earnings within 5 days are flagged everywhere. This is the VST lesson.
  • Stopped-out names go on re-entry watch. Reclaiming the exit price or the 20-day MA brings them back as candidates. This is the NBIS lesson.
  • Cash above 10% must be evaluated every run — through opportunity criteria, exit defined before entry, never mechanically. Your rule. Now backed by a real ranked candidate list rather than ad-hoc research, and since v2.7 by the FRM's gate v2, which measures reward against a momentum target at ≥1.5:1 instead of against a consensus price target at >2:1. The ladder's session-counting retires when frm_enabled flips to 1; its honesty obligation does not — every FRM night states a target cash % and the reason for it, whether or not anything is proposed.
  • Every exit gets scored monthly against "what if we'd held". As of v2.3 every brief action is scored at 5/20/60 days too — not just exits.
  • Reconciliation is one screenshot away, so table drift never accumulates.
  • Tier 1 rails are enforced in code, not judgment. No single name above 35% of the book, no single factor above 65%, cash between 0 and 40%, leveraged ≤15% of the book and ≤10% in any one instrument, at most 20% of book value deployed in a single session, no order under $10, no new entry within 24h of a red-severity event on that name or on the market, and stops never lowered. A proposal that breaks one is rejected before it ever reaches you, and Market Watch re-checks the rails against the live book at fire time rather than the book as it stood at arming.
  • The old caps are bands now, not law. Single name 20%, single factor 45%, the layer bands (Core 50–60%, Amplifiers 20–30%, Tactical 0–20%), the anti-correlation requirement and cash at 5–15% in a risk-on tape are defaults the FRM steers toward. It may breach one — but the proposal has to name the band, the size of the breach and the reason, in the brief and on the scoreboard, where band-breach calls are tagged so their hit rate reads separately. If judgment-overrides underperform the defaults, that is the system telling you to narrow Tier 3.
  • Leveraged vehicles are railed, not banned — entry.leveraged_allowed was flipped to 1 on 20 Aug. The rejected backtest still stands as the reason they are not held casually, so the rails are tight: ≤15% of the book in total, ≤10% in any single one, proposable only at regime score ≥3, and a 25% stop cap rather than 15%, because a 15% stop on a 3× instrument is one day's range.
  • Only one thing can decide: the 5:00 PM brain. Weekly and monthly reviews audit and score; they never write an action.

02Resolved incidents

Resolved 2026-08-14

"Actions needed: none" while the brief said raise the OUST stop

The 6:30 AM digest showed Actions needed → none today while the brain brief immediately below it said "OUST: raise stop 37.50 to 40.95". Missed for two consecutive days.

Two independent faults, and both had to be fixed

Fault 1 — the brief was never wired to the action list. The two sections come from different places: actions from positions_state.pending_action, the brief from daily_brief.brief_text, a free-text blob. Build Digest computed pendings = open.filter(p => p.pending_action). Nothing ever read brief_text, and Brief Intake had no channel to write pending_action. So any judgment call the brain made lived in prose only, invisible to the action list.

Fault 2 — manual_override = true on OUST blocked the only writer that existed. Market Watch guards the ratchet with if (!p.manual_override && p.trail_pct && stop). The flag was set on both TSM and OUST at build time. For TSM that is correct — its 364 stop and 460 TP are hand-chosen. For OUST it was wrong: a plain 15% trailing-stop rule with nothing hand-picked about it. Net effect: OUST was double-blocked. The watcher refused to write the action; the brain had no way to.

Fix: Brief Intake gained actions[], clear_actions[] and flags[]; OUST came off override; and Build Digest gained the brief-vs-state reconciliation pass. TSM keeps manual_override = true by design.
Amended 19 Aug 2026. This entry used to claim the reconciliation pass made the failure "structurally unrepeatable even if a future writer path breaks". It did not. The pass read the level out of the brain's prose, and on 18 August a rephrased action defeated it — see the post-mortem below. The claim holds only now that the level is a column.
Resolved 2026-08-14

The analysis was timely; the delivery was a full session late.

Money read aloud with the punctuation attached

The spoken-script builders rewrote $185. as "185. dollars" and $180.79, as "180.79, dollars", because the pattern /\$\s?([0-9][0-9,.]*)/ greedily consumed the trailing full stop or comma into the number.

Inherited from the v1.1 digest build, so it had been in every audio brief since 14 August. Tightened to /\$\s?(\d{1,3}(?:,\d{3})+(?:\.\d+)?|\d+(?:\.\d+)?)/ and fixed in all three script builders at once.

The Nightly Screen's n8n description and its canvas sticky note both stated it ran at 02:00 IST and "posts a Telegram summary". The trigger is 16:45 IST and there is no Telegram node in the workflow at all — there never was.

Harmless in operation, but exactly the kind of thing that costs an hour six months later when someone goes looking for a message that was never designed to exist. Both corrected; the sticky now says so in as many words.
Resolved 2026-08-19

Five actions pending, zero buttons to confirm them

The 18 August digest arrived with five pending actions and not one ✅ Done button. Execution 4358, status success, the workflow untouched since the 17th — same versionId throughout. Nothing broke. The brain simply phrased that day's actions differently than the day before.

A regex over prose is a contract nobody signed

What the code was looking for. Six code nodes across four workflows carried the same literal /raise stop to ([0-9.]+)/i. What the brain actually wrote that day was raise stop 181.60 to 182.34 (20% below true 20d high 227.92) and place/raise hard stop to 346.18 — the Aug 17 stop order was REJECTED…. None of the five matched, the keyboard rows came out empty, and the count router fell through to the one send node that has no keyboard by design. On that branch buttons were structurally impossible. On the 17th a single action happened to be phrased raise stop to 42.62 — which is why exactly one button rendered that day, and why the failure looked partial rather than total.

Every route to confirming was dead, not just the buttons. /done used the same regex, skipped every row, and replied "Nothing pending 🎉" against five pending actions. The typed fallback the digest itself printed led to "no recommended level is pending". The system was not merely unhelpful that evening — it was confidently wrong in three places at once, and every one of them reported success.

The one-line fix would have been worse than the bug. Widening the regex was blocked at the pre-upgrade gate, tested against the day's real strings. The widened capture spans " — the Aug " and mints done:AVGO:17.00 on a $392 stock; on NVDA it greedily takes 227.92, above the last traded price, so one tap is an instant stop-out. The callback handler trusted whatever level rode the wire absolutely. The obvious change would have converted a cosmetic bug into a money-path one.

Fix: the level moved into positions_state.pending_stop_level, and all six sites now read it through one shared guarded reader — column first, anchored regex only as a transitional fallback, then guards for finite and positive, strictly above the resting hard_stop, below last_price, and not below half of it. No valid level, no button. Taps re-read the row rather than trusting what the button carries. Verified offline — 33/33 on the guard suite, 12/12 on an independent adversarial pass against the server-stored code — because the digest messages you for real and so can never be used as a test. Confirmed live on retrigger: execution 4393, three keyboard rows returned.
The lesson the system now encodes: the code never changed — the data did. Anything that recovers a number from model-written prose is an unwritten contract between a writer free to rephrase and a reader not allowed to, and it fails on the day the writer exercises that freedom. The structured column is the contract. The regex that remains is transitional, and it still cannot see negation.

03Validated & rejected

Two rule candidates were backtested on 14 Aug 2026 and both rejected. Recorded here so they aren't re-proposed without new evidence.

Rejected

Leveraged-ETF volatility gate

Tested across all four leveraged pairs in the universe — SOXL/SMH, DFEN/ITA, ERX/XLE, LABU/XBI. The gate was anti-selective in every pair: the days it excluded outperformed the days it included, and this held at every threshold tested from the 40th to the 75th percentile. There is no percentile cut of this gate that helps. SOXL, DFEN, ERX and LABU therefore stay in universe as measurable, for relative-strength context, but are forbidden as holdings via entry.leveraged_allowed = 0.

Amended 20 Aug 2026. leveraged_allowed is now 1. What this backtest killed was the timing gate — the claim that a percentile filter could tell you which days to hold a 3× instrument — and that finding stands. It was never evidence that a leveraged position is unholdable at any size. Under the FRM the four are proposable inside hard rails instead: ≤15% of the book in total, ≤10% in any single one, regime score ≥3, and a 25% stop cap rather than 15%. See the FRM card.
Rejected

ATR-scaled stops

Rejected for a measurement reason rather than a performance one: no stop rule can be validated yet, because every historical stop-out predates the 11 August build and was set by hand. The backtest would have been measuring a rule that never actually governed those exits. Revisit once enough stop-outs have occurred under the live tiered-trail rule.

04Bugs fixed along the way

Every one of these failed silently. That is the pattern worth remembering.

n8n

Silent no-op runs

An executeOnce setting truncated the position list to a single item, so Market Watch "succeeded" sixteen times a day while doing nothing. Fix: nodes read upstream data by explicit reference — $('Node').all() — never by implicit input item.

n8n

Vanishing buttons

n8n's Telegram node silently discards dynamically-built inline keyboards. The message sends fine; the buttons simply aren't there. Fix: the keyboard shape is literal and only the labels and values are expressions — which is why there are n=1..6 send variants routed by button count.

TwelveData

Shape-shifting API

TwelveData returns {"price":"1.23"} for one symbol but {"AAPL":{"price":"1.23"}} for many. Code written against the many-shape breaks the day a batch has one item. Fix: responses are normalised at the boundary, before any business logic touches them.

n8n

The chunk loop that only ever read chunk zero

The Nightly Screen's Normalize Chunk Prices node resolved chunk metadata via itemMatching(0), pinning every chunk's metadata to the first chunk — so only the first 6 of 45 symbols ever produced real data. Silently. Fix: the node is now metadata-free and derives each symbol from its own API response. Verified 45/45 symbols, 260 bars each.

n8n

The seventeen-times alert

Adding a Get Config node upstream of Get Open Positions caused an unintended per-item fan-out — 5 positions crossed with config rows multiplied to 85 items — producing one Telegram message with the same alert repeated seventeen times. Fix: executeOnce on the positions node, so config is read once per run rather than once per position.

The lesson the system now encodes: a workflow reporting "success" is not evidence that it did anything. Verify by observable outcome — did a row change, did a message arrive with the thing in it. The daily digest, the heartbeat and the failure monitor all exist so that silence gets noticed.
